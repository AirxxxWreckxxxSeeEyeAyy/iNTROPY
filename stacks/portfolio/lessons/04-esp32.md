# ESP32 and IDE workflow

Project: P04. Prerequisites: F1–F3. Identify the currently attached device before following any hardware-specific procedure.

## E1 — Identify the board and recovery route

**Learn:** chip versus development board, flash size, pin mappings, serial ownership, boot modes, and firmware provenance.

**Practice:** reconcile physical markings, chip information, vendor documentation, and serial boot output. Record the exact display/touch controller and framework supported by the vendor project. Locate the user's existing firmware backup and record its hash privately; do not create an unnecessary duplicate.

**Pass:** E-01 has no unresolved conflict between target, flash layout, and chosen image. The saved historical board identification is a lead, not current proof.

**Save:** board manifest, redacted boot output, vendor source links, image/build hashes, and recovery plan.

## E2 — Reproduce a source build in the IDE and terminal

**Learn:** source, compiler/toolchain, board package, dependency versions, build output, and serial monitor configuration.

**Practice:** use Arduino IDE for a vendor-supported Arduino sketch, or ESP-IDF with its VS Code extension for an ESP-IDF project. Choose one path first. Build a minimal supported example and record the same project's command-line build process.

**Pass:** E-02 builds from a clean checkout with recorded versions. If the vendor provides only a binary, label that exercise “binary restoration”; obtain a separate supported source example for the build lesson.

**Save:** minimal source, dependency/configuration manifest, build logs, and firmware hash. Binary hashes need not match across builds if timestamps or metadata are embedded; investigate and document differences.

## E3 — Verify actual device behavior

**Learn:** build success, flash verification, and correct runtime behavior are separate outcomes.

**Practice:** after E-01 and recovery checks pass, close competing serial monitors and follow the exact board/vendor flashing procedure. Capture boot output and a functional demo. For a display project, define a test pattern and touch grid with expected responses.

**Pass:** E-03 completes three cold starts and ten defined input checks without an unexplained failure. Those counts are a starter lab target, not reliability certification.

**Save:** flash output, serial log, short video/photos, and an input-versus-result table.

## E4 — Diagnose, recover, and maintain

**Learn:** isolate configuration, firmware, peripheral, and power faults; recover a known-good state.

**Practice:** reproduce a reversible software/configuration error. Restore the known-good image/configuration using documented offsets and options, then repeat the functional checks.

**Pass:** E-03 recovery succeeds and the operating procedure identifies the root cause. Do not use destructive electrical faults or experimental fuse changes as a beginner exercise.

**Save:** fault description, recovery timing, verified image identity, and regression checklist.

Reference: [Espressif build/flash/monitor workflow](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/get-started/start-project.html) and [official IDE workshop](https://developer.espressif.com/workshops/esp-idf-setup/). Use documentation matching the selected SDK and board; generic ESP32 settings do not establish compatibility with a particular display.
